# DEVIATIONS

Append-only log of every place HIVE-LOCAL substitutes something for the production HIVE
platform. This file is the migration checklist: each row is a thing that must be swapped
back before or during migration to the official platform.

Add a new row the moment a substitution is made — including any reliance on `amd64`
emulation via Rosetta (see the working agreements in [CLAUDE.md](CLAUDE.md)).

## Seeded deviations

| Local | Production |
|---|---|
| Fake GPU extended resource patched onto node capacity | NVIDIA GPU Operator + DRA (**same request surface**: `resources.limits["nvidia.com/gpu"]`) |
| `kind` cluster + Calico CNI | Rocky Linux on bare metal |
| `local-path` StorageClass | WekaFS CSI with directory quotas |
| Kourier + `kubectl port-forward` | MetalLB + Kong, with Keycloak tokens |
| 60s idle windows (`window` / `scale-down-delay`) | 30m idle windows |
| 10-minute TTL grace period | 14-day TTL grace period |
| No identity layer locally | Keycloak-backed identity and token issuance |

| **STUDIO'S REAL EXECUTOR MIRRORS THE InferenceService TO THE HOST ITSELF, rather than relying on the Fallback-B syncer.** `RealExecutor.inference_service` applies the isvc INSIDE the tenant's vCluster (the tenant is the author) and then applies a mirrored copy into the host namespace as `<project>-x-default-x-<project>`, labelled `hive.ksl/managed-by=studio-executor` and `hive.ksl/project=<project>`. | vCluster's own toHost custom-resource syncer, running inside the vCluster control plane. Identical to the Fallback-B target — one syncer serves every tenant, hand-built or Studio-created. | 2026-08-23 | **Cause: [scripts/sync-isvc.sh](scripts/sync-isvc.sh) cannot serve a Studio project.** Its tenant list is hard-coded (`TENANTS_DEFAULT=("inf-101:p-inf-101" "inf-103:p-inf-103")`) and it rejects any other name with a usage error, and it is a polling daemon that must already be running. A console that provisions on demand cannot depend on either. **The architecture shape is unchanged and this is the point: the tenant still AUTHORS inside their own control plane, and the ONE central KServe still RECONCILES on the host** — only the mirroring mechanism differs, and it is now deterministic and part of the pipeline rather than an external loop. Honest limitations: the mirror happens ONCE, at deploy time, so a tenant editing their isvc afterwards is not re-mirrored (the script polls every 10s and would be); and status flows back as `hive.ksl/host-*` annotations written once by `ready-check`, not continuously. **At migration all of this is deleted together with Fallback B** — uncomment `sync.toHost.customResources` in `templates/t-*-values.yaml` and the executor's mirror step becomes a no-op to remove. The alternative considered and rejected was extending `sync-isvc.sh` to take arbitrary `name:namespace` pairs: it would still be a daemon, and a Studio deploy that silently does nothing because nobody started a script is a worse failure than one extra `kubectl apply`. |
| **Tenant GPU quota is `tier + 1` (2), not the tier (1), because Knative's dry-run validation consumes quota.** Both `p-inf-101` and `p-inf-103` have `requests.nvidia.com/gpu: "2"` while their documented tier is 1 GPU. | A GPU quota equal to the tier, with the tier provably enforced by the ResourceQuota alone. | 2026-08-18 | **NEEDS A PLATFORM-LEVEL DECISION — this is not purely local.** Knative's validating webhook dry-run-creates a sample pod to validate every Revision template, requesting the same resources as the real pod (`pkg/webhook/podspec_dryrun.go`, **unconditional in v1.23 — no feature flag, no annotation gate**). With a ceiling of exactly 1 and the real pod holding it, the dry-run can never pass: `dry run failed with pods "dry-run-validation..." is forbidden: exceeded quota ... used: 1, limited: 1`. KServe then retries forever and the InferenceService is pinned at `READY=False` **even though the pod is Running and the Knative Service, Route and Revision are all Ready**. Confirmed by experiment: raising to 2 made it Ready in ~20s. Worst for T-AO, which never releases its GPU and so is permanently stuck; T-SZ self-heals when idle, i.e. fails intermittently. **The same constraint applies in production** — any Knative-backed KServe tenant with an exact-fit GPU quota hits it, and rolling updates need headroom for the same reason. **Consequence: the enforced concurrent ceiling is now 2, so a determined tenant could run two 1-GPU pods; the quota alone no longer proves "Medium = 1 GPU".** Options: accept the headroom and enforce the tier elsewhere (cap `count/inferenceservices` at 1 *and* pin `max-scale`), or use an admission policy that can distinguish a dry-run from a real pod. |
| **FALLBACK B — syncer stand-in pending vcluster fix.** InferenceServices authored inside a tenant vCluster are mirrored into that tenant's host namespace by [scripts/sync-isvc.sh](scripts/sync-isvc.sh), a polling script, instead of by vCluster's `sync.toHost.customResources`. Host status is mirrored back to the virtual object as `hive.ksl/host-*` **annotations**, not `.status`. Mirrored objects are named `<name>-x-<namespace>-x-<vcluster>` and labelled `hive.ksl/managed-by=sync-isvc`. | vCluster's own toHost custom-resource syncer, running inside the vCluster control plane, writing real `.status` back. | 2026-08-18 | **Cause: `sync.toHost.customResources` is a vCluster PRO feature** (`Generic Sync` / `vcp-distro-generic-sync`). Open-source v0.36.1 accepts the config and reports a successful `vcluster create`, then the control-plane pod crash-loops with *"you are trying to use a vCluster pro feature 'Generic Sync' … not available in the open source vcluster"*. Not a bug and not debuggable — a licence gate. **Architecture shape is preserved: the tenant AUTHORS inside their own cluster; the ONE host KServe RECONCILES.** Honest limitations: it POLLS (default 10s) so propagation lags in both directions; status arrives as annotations rather than `.status`; the virtual object is **not** validated by KServe's admission webhook (that lives on the host), so a malformed spec is rejected late; and **if the script is not running, nothing is mirrored** — a real syncer shares the control plane's lifecycle. At migration: uncomment the `sync:` block in `templates/t-*-values.yaml`, delete this script, delete this row. No tenant-authored manifest changes. |
| **FALLBACK A — host ClusterServingRuntime catalogue copied into each vCluster.** [scripts/sync-catalog.sh](scripts/sync-catalog.sh) copies the CRD and all 14 host `ClusterServingRuntime` objects into each tenant vCluster, labelled `hive.ksl/managed-by=host-catalog-sync` and `hive.ksl/read-only=true`. | vCluster's `sync.fromHost.customResources` with `scope: Cluster`, which is read-only **by construction**. | 2026-08-18 | Same root cause as Fallback B — `fromHost` custom-resource sync is the same Pro `Generic Sync` feature; verified independently by enabling *only* the fromHost stanza, which crash-loops with the identical error naming `clusterservingruntimes.serving.kserve.io`. **Read-only here is BY CONVENTION, not enforced.** A tenant is cluster-admin inside their own vCluster and can edit these copies; the next script run overwrites them. That is strictly weaker than real fromHost sync and is the main thing to re-verify after migration. What it does preserve: the catalogue is authored on the host, so no tenant can change what another tenant's `modelFormat: sklearn` resolves to. Re-run the script whenever host runtimes change. |
| **Tenant `requests.storage` quota raised to 12Gi (from 5Gi) and `persistentvolumeclaims` to 6 (from 4)** to accommodate the vCluster control plane. | Sized against real WekaFS capacity with directory quotas; the control-plane volume is budgeted deliberately rather than discovered. | 2026-08-18 | The vCluster StatefulSet provisions its own **5Gi etcd data PVC inside the tenant's host namespace**, which counts against the tenant quota. With the original 5Gi ceiling and 2Gi already used by `models` + `scratch`, the control plane could never start. Failure shape worth remembering: the StatefulSet retries forever and **no pod is created at all**, so `kubectl get pods` is empty and the only explanation is in the StatefulSet's events. GPU remains the binding tier constraint; storage is deliberately roomy locally, for the same reason cpu/memory are. |
| **InferenceService URLs carry a `-predictor` segment, because there is no Istio.** KServe's `ingress.disableIstioVirtualHost` is set to `true` ([host/serving/kserve/ingress-config-patch.yaml](host/serving/kserve/ingress-config-patch.yaml)), so `.status.url` is the predictor's Knative route: `http://sklearn-iris-predictor.default.hive.local`. | Istio (or Kong) serves the short form `http://<isvc>.<namespace>.<domain>` via a `VirtualService`, with `disableIstioVirtualHost` left at its default `false`. | 2026-08-17 | Discovered at Gate G1: with the shipped default, KServe strips `-predictor` from the route host and advertises a hostname **only an Istio VirtualService would serve**. Since HIVE-LOCAL runs Kourier and KServe skips VirtualService reconciliation when the Istio CRD is absent, the InferenceService reported `READY=True` while its advertised URL returned **404 in 8 ms without waking a pod** — a silent failure with no unhealthy condition anywhere. **Migration consequence: the tenant-facing hostname SHAPE differs between local and production.** Nothing may hard-code a hostname; always read `.status.url`. At migration, flip this flag back to `false` and the short form returns with no change to tenant manifests. |
| **`amd64`-only serving runtime images, run under Rosetta emulation if used.** The step-3 control plane is entirely native `arm64` (cert-manager, Knative Serving, net-kourier, Envoy, KServe controllers, `kserve/sklearnserver`, `kserve/xgbserver`, `nvcr.io/nvidia/tritonserver` all publish `linux/arm64`). Two `ClusterServingRuntime` images do **not**: `kserve/huggingfaceserver:v0.20.0` and `docker.io/seldonio/mlserver:1.7.1` (used by the `kserve-mlserver` runtime) are `linux/amd64` only. | Native `linux/amd64` on Rocky Linux bare metal — no emulation, and the same runtimes are the normal choice there. | 2026-08-17 | Nothing installed in step 3 currently *relies* on emulation: the runtimes are declared but no `InferenceService` uses them yet. The moment a tenant selects the HuggingFace or MLServer runtime, that pod runs under Docker Desktop's Rosetta `amd64` emulation — slower, and with occasional differences in low-level behaviour. **This matters for Inf-101, which CLAUDE.md defines as an LLM service**, the natural fit for `huggingfaceserver`. Options when we get there: prefer an `arm64`-native runtime locally (`kserve-sklearnserver` / `kserve-xgbserver` for the scheduling and lifecycle rehearsal, which is what HIVE-LOCAL actually tests), or accept emulation and note the performance numbers as non-representative. Either way, **model-serving performance measured locally must never be quoted as a production expectation.** |
| Fake `nvidia.com/gpu` extended resource patched onto node status — **4 per worker, 8 cluster-wide** — via the documented node-status `PATCH` mechanism, applied by [scripts/fake-gpus.sh](scripts/fake-gpus.sh). Workers also labelled `hive.ksl/gpu-pool=shared`. | NVIDIA GPU Operator + DRA on real GPU hardware, advertising real `nvidia.com/gpu` capacity. | 2026-08-16 | **The request surface is identical** — tenants ask for `resources.limits["nvidia.com/gpu"]` in both worlds, so tenant manifests migrate unchanged (CLAUDE.md §2.3). **No device plugin is used, and none may be introduced.** Only scheduler *accounting* is real locally: the scheduler counts requests against advertised capacity and refuses to overcommit, but nothing is isolated or executed on a GPU. **Not durable** — the kubelet is the authority for its own node status, so any kubelet restart (Docker Desktop restart, cluster restart, `docker restart hive-host-worker`) wipes the patch; symptom is pods Pending with `Insufficient nvidia.com/gpu`. | **FALLBACK A, SECOND HALF — the `InferenceService` CRD is copied into each hand-built tenant vCluster** by [scripts/hive-up.sh](scripts/hive-up.sh) (phase 7), with the same `--server-side` apply and the same `hive.ksl/managed-by` label as the `ClusterServingRuntime` copy in [scripts/sync-catalog.sh](scripts/sync-catalog.sh). | vCluster's `sync.fromHost.customResources`, which publishes the KServe API surface into every tenant cluster read-only **by construction**. | 2026-08-27 | **This was previously a manual act that no file recorded.** During step 6 the isvc CRD was applied into both vClusters by hand, so `tenants/inf-101/legal-translation.yaml` applied cleanly on that machine and nowhere else — a cold rebuild produced two vClusters in which the tenant's own `kubectl apply` fails with *"resource mapping not found"*, which reads like a bad manifest rather than a missing API. | **THE RAG STACK'S NON-KSERVE COMPONENTS RUN IN THE TENANT'S HOST NAMESPACE, NOT INSIDE THEIR vCLUSTER.** Qdrant (a single-replica Deployment + Service + PVC), the ingestion Job and the RAG service are all applied to `p-<project>` and labelled `hive.ksl/template=studio-rag`. Only the chat `InferenceService` is authored inside the vCluster. | The same split, or none of it: with a ReadWriteMany filesystem the ingestion Job could run inside the tenant's own control plane, and the vector database could be a platform service the tenant addresses rather than one that lives in their namespace. **This needs a tenancy-model decision before migration.** | 2026-08-31 | **Cause: a pod authored inside a vCluster CANNOT MOUNT THE EXISTING HOST PVCs.** The syncer maps a virtual PVC to a NEW host PVC, so an in-vCluster ingestion Job would mount an empty volume, index nothing, and report success — a silent failure, which is the worst kind. KServe's predictor pods are already host-native for the same family of reasons, so this is the tenancy model the platform already has rather than a new one. **Honest consequences, both tenant-visible:** the PI cannot `kubectl edit` their own Qdrant — they reach their index only through their RAG endpoint and the project page; and the vector database counts against their host ResourceQuota, which is correct but means a tenant's own storage headroom is smaller than the tier number suggests (see the `rag-small` profile). **What is NOT a deviation here:** the chat model is still authored by the tenant inside their own vCluster and reconciled by the ONE central KServe on the host (CLAUDE.md §2.1, §2.2). The RAG template does not weaken that, and `templates/catalog/rag-stack/resources/inference-service.yaml.tmpl` is the file to check it against. |
| **THE RAG TOOLKIT IMAGE IS BUILT ON THE LAPTOP AND PUSHED INTO THE NODES WITH `kind load`, SO EVERY POD USING IT SETS `imagePullPolicy: Never`.** `hive-local/rag-toolkit:0.1.0`, built from [studio/images/rag-toolkit/](studio/images/rag-toolkit/) by [scripts/build-rag-toolkit.sh](scripts/build-rag-toolkit.sh). It exists in no registry. | A versioned, signed image in the platform registry, pulled normally, with `imagePullPolicy` left at its default. | 2026-08-31 | There is no registry in this rehearsal, and pushing to a public one to run a laptop demo would be worse than building locally. **The failure this causes if the `Never` is ever dropped is genuinely confusing:** the kubelet tries Docker Hub for `hive-local/rag-toolkit`, the pod sits in ImagePullBackOff, and `docker images` on the host clearly shows the image is present — because the host daemon and the nodes' containerd are separate stores. `RealExecutor.approve` therefore runs the build script as a precondition on every RAG deployment (it is idempotent and skips both the build and the load when they are unnecessary) and then verifies that the image the RENDERER names is the one the nodes hold. At migration: publish the image, delete the three `imagePullPolicy: Never` lines and the `approve` precondition. |
| **A PI's DOCUMENTS REACH THEIR PROJECT BY `kubectl cp` INTO A THROWAWAY POD.** The `corpus-upload` step starts `<project>-stage` (busybox, `sleep 600`) with the `scratch` PVC mounted, copies `tenants/_uploads/<id>/` into it, verifies the file list *inside the pod*, and deletes the pod in the same step. | An upload service writing to shared storage the tenant already has mounted, with re-indexing when the documents change. | 2026-08-31 | **A PersistentVolumeClaim is not writable from outside the cluster**, and `kubectl cp` copies into a CONTAINER rather than into a volume — so getting files onto `scratch` requires a running pod with `scratch` mounted for as long as the copy takes. The alternatives were considered and are worse: a ConfigMap caps at 1MiB and a corpus is not configuration; baking the corpus into an image means a rebuild per upload; an in-cluster HTTP upload endpoint is a second exposed service with its own authentication story, to move files once. **Two real limitations, both stated in the template's `corpusUploadId` help text rather than hidden:** the corpus is copied ONCE, at provisioning, so changing documents means redeploying; and there is no access control on the corpus beyond the tenant boundary — anyone who can reach the project's endpoint can retrieve any passage in it. **One trap worth keeping:** `kubectl cp` is implemented as `tar cf - … \| kubectl exec -i -- tar xf -`, so the target container needs `tar` on its PATH. busybox has it; a `scratch` or distroless image would fail with "tar: not found", which reads like a permissions problem. |
| **THE RAG SERVICE REACHES ITS CHAT MODEL BY HAIRPINNING THROUGH KOURIER'S CLUSTER-LOCAL GATEWAY (`kourier-internal.kourier-system`) WITH A `Host:` HEADER.** The service name is DISCOVERED at deploy time (the ClusterIP Service in `kourier-system`), and the host comes from the InferenceService's live `.status.url`. | The same shape through whatever local gateway the production Knative install uses — `knative-local-gateway.istio-system` with Istio. Only the service name changes. | 2026-08-31 | Knative routes by Host header through a gateway, and **the gateway is also what WAKES a scaled-to-zero revision** — so an in-cluster caller must go through it rather than addressing a pod, or an on-demand project could never be woken by its own RAG service. This is the same mechanism the playground uses from outside through a port-forward, and the architecture shape is production's. What differs is only the gateway's name, which is why the executor discovers it by TYPE and logs what it found instead of hard-coding one. **The `Host` value is never constructed** — locally KServe publishes a `-predictor` segment production will not have (see the `-predictor` row below), so `ready-check` reads `.status.url` and hands it to the `rag-api` step; the dry-run preview shows the reserved sentinel `resolved-at-deploy-time.invalid` instead, which can never resolve if it ever leaked. |
| **THE RAG DEMO ANSWERS COME FROM A 0.5B MODEL, AND ANSWER QUALITY MEASURED HERE IS NOT REPRESENTATIVE.** `qwen2.5-0.5b-instruct-q4` on CPU, served by `hive-llama-cpp-rag` with a 4096-token context (`host/serving/runtimes/llama-cpp-rag.yaml`). | The model the research group actually needs, on real GPUs, with whatever context that model supports. | 2026-08-31 | The same substitution the two hand-built tenants make for the same reason: **the deliverable is the platform's behaviour, not model realism.** What this build genuinely proves is the retrieval half — that a corpus is chunked deterministically, embedded with the same model at index and query time, searched, and returned with citations a PI can check. Verified end to end on 2026-08-31 against the demo corpus: a question the corpus answers produced a correct, cited answer; a question it does not ("Who is the current Queen of England?") produced the exact refusal string with the model declining to fill the gap. **A weaker answer from a bigger prompt is a model limitation and not a pipeline fault**, which is why `rag-ready-check` records the smoke answer in the step log rather than asserting anything about its content. **The context number IS load-bearing and does not scale away:** a runtime whose context is too small does not fail, it TRUNCATES from the front, where the retrieved passages are — which is why `topK` is capped at 8 and why the runtime is pinned by the template rather than taken from the catalogue entry. |
